# 教学视频的动效预算：中段为什么"活"不起来

这份文档记录一次针对"场景中段整屏静止"的排查。结论先说：**这不是动效不够，
是构图太小、内容面积不够**；而且原来定的"中段活跃块 15%"这条验收线在该内容
形态下数学上不可达，已经作废。

## 1. 口径（先对齐怎么算"在动"）

`scripts/measure-motion.py` 三层拆：

| 口径 | 定义 | 量的是 |
|---|---|---|
| 静帧率 | 相邻两帧全画面灰度 MAE < 0.5 | 画面有没有"完全冻住" |
| 活跃块占比 | 16×9 网格里，单块（120×120）MAE ≥ 1.5 的块占比 | 有几处地方在变（最接近眼睛） |
| 可感知变化事件 | 连续 MAE ≥ 1.0 的段落数 / 秒 | 变化的"次数" |

两个关键数字含义：

- **活跃块 1.5 的门槛** ≈ 一块 120×120 里约 216 个像素变化 100 灰阶，也就是
  边缘移动约 2px。**位移小于 2px 的运动，这个口径一律测不出来。**
- **静帧 0.5 的门槛**是全画面平均，约等于 1 万像素变化 100 灰阶。局部小面积动
  （一个 200px 的卡片呼吸）摊到 207 万像素上只有 0.01~0.02，永远过不了。

所以这两个指标都是**面积型**的：偏袒大面积运动，对细线流光、字体边缘天然失明。
任何"加一点微动"的直觉，都过不了这两道闸。

## 2. 已试并否掉：beats 编排

仓库里有一套句级编排层（`video/choreography.ts` → `scene.choreography` → 渲染层
`beatStateAt()` 解释器），会把旁白每句编译成一拍，带帧窗、焦点、揭示、动效预设。
直觉上这正是"讲到哪、画面变到哪"，应该能救中段。

用同一份场景做了受控对照（`Root.tsx` 里 s1 与 b1：同内容、同关系图、同 200 帧，
**唯一变量是有无 choreography**）：

| 指标 | 无编排 | 有编排 |
|---|---|---|
| 静帧率（全片） | 83.4% | 78.9% |
| 静帧率（中段） | 94.2% | 90.8% |
| 最长静止连续段 | 20 帧（0.7s） | **55 帧（1.8s）** |
| 主画布 MAE | 0.390 | 0.389 |
| 活跃块占比（中段） | 4.2% | **3.5%** |
| 可感知变化事件 | 1.81 次/秒 | **0.75 次/秒** |

**更差了。** 看渲染帧就明白：b1 的 reveal 把节点推迟到各自的拍才入场，第 100 帧
（中段）画面上只有 2 张卡，连环形箭头都被 `edgeGate` gate 掉了。"分段揭示"的
代价是**把画面变空**——空画面比静止画面更糟。

结论：beats 是叙事结构（讲到哪强调哪），不是动效来源。不要指望它提中段指标。

## 3. 根因：空白稀释

放大前的 cycle 场景：4 张 186px 节点卡排在一个 536×404 的椭圆环上，整组只占
**722×590**，在 1920×1080 里左右各留 600px 空背景。而其中只有"当前焦点"那 1 张
卡在呼吸（占屏幕 2.2%）。

算一下上限就清楚了：

- 4 张卡全动，卡面积 4×186² ≈ 13.8 万 px = 屏幕 **6.7%**
- 加上环线、标题、字幕，全动满也就 **9%**

这就是实测 4.2% 的天花板由来——**不是动效没生效，是能动的面积就那么多**。

## 4. 做了什么：构图放大一档

六种关系的节点尺寸/半径统一放大（`layoutGraph`）：

| 关系 | 原尺寸 | 新尺寸 |
|---|---|---|
| cycle | 卡 186，环 268×202 | 卡 232，环 322×196 |
| chain | 卡 206，步距 500 | 卡 244，步距 528 |
| growth | 172 + i×40 | 196 + i×44 |
| compare | 262 | 300 |
| group / split | 父 190/200，子 168/156 | 父 216/228，子 192/180 |

约束校验（都靠 `y≈860` 字幕条顶边和 `y≈174` 的 caption 底边卡着）：

- cycle 顶部卡顶 188 > 174 ✓；底部标签底 856 < 860 ✓
- 六种关系各渲一帧目检，无卡片重叠、无越界、无压字幕

效果（前 5 场景 999 帧，与 A+B 基线同区间）：

| 指标 | 放大前 | 放大后 |
|---|---|---|
| 活跃块占比（全片） | 7.66% | **8.30%** |
| 活跃块占比（中段） | 4.51% | **5.20%** |
| 主画布 MAE | 0.765 | **0.855** |
| 可感知变化事件 | 26 次 | 27 次 |
| 空画面 | 2 帧 | 2 帧（未退化） |
| 切点亮度摆幅 | 9.12 / 8.36 / 7.47 / 8.16 | 9.00 / 8.30 / 7.40 / 8.00 |

单场景纯净对照（同 props、只差布局）更能说明幅度：活跃块中段 4.2%→5.0%，
主画布 MAE 0.390→0.469（+20%）。

**静帧率没变**（94.2% 两边一样），这符合预期：放大不改变"有没有动"，只改变
"动的时候幅度多大"。要降静帧率只能靠大面积高对比变化（切点转场、字幕）。已经
降到 82% 是字幕带逐字点亮的功劳，顶部主画布降不动。

## 5. 为什么"中段活跃块 15%"不可达（已作废）

活跃块 15% = 144 块里 21.6 块每帧都在变 = 全屏 **15% 的面积每帧都在变化**。

对比：一条 1670px 长、30px 宽的光带以 20px/帧 移动，每帧"变化面积"约 600px²
= 全屏 **0.03%**。差 500 倍。

15% 这种量级只有整屏转场、大幅运镜或全屏动画能做到——广播级动画里也罕见。一屏
只讲 3-4 个概念的教学分镜，内容面积上限就 20%，15% 不可能。

**新的合理线**（按内容面积反推）：

- 静帧率（中段） < 85%
- 活跃块占比（中段） 6% ~ 9%
- 可感知变化事件 1.5 ~ 2.5 次/秒

## 6. 顺带确认的两件事

- **growth 的"大树比小花小"不是 bug**。第 100 帧时 `storyProgress≈0.41`，大树的
  `growWindow` 是 [0.6, 0.9] 还没轮到它长，`scale` 停在 0.42。到后段会最大。
- **split 的"树根"、group 的"香蕉"不是空白卡**。缩略图分辨率太低看不清，原图上
  有绿色文字/图标（无 `graphIcons` 时走 `glyph` 回退显示 label 前两字）。

## 7. 复验

```bash
cd src/backend && node scripts/preview-prepare.js
cd ../video-remotion && ./node_modules/.bin/remotion render src/__preview/index.ts \
  LessonPreview out/seq-big/frames --sequence --image-format=png --frames=0-999
cd ../backend && python scripts/measure-motion.py --dir ../video-remotion/out/seq-big/frames \
  --json ../video-remotion/out/motion-big.json
```

单关系目检：用 `--frame=100 --props=<单场景 props>` 渲 still，六种关系拼图对照。

注：Remotion CLI 会调 `wmic` 探测进程，在受限环境下会被拦并打印
`PROGRAM BLOCKED BY SECURITY POLICY`，该异常内部被捕获，不影响渲染（报告为准）。
