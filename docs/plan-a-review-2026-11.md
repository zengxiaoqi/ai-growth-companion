## 0. 结论先行

**评审建议：暂缓 P2（No-Go），先用零生产代码的三个门禁补齐决策依据。**

理由不是「方案 A 技术不可行」——恰恰相反，P0 PoC 已把运行时承载链路验证得很扎实。阻塞在于三件与工程量无关的事：

1. **文档自己设定的准入门槛尚未满足**：§7.1 要求「P0 报告证明价值显著」才能进 P2，§10 要求学习效果对照实验至少 2 项指标显著优于参数化题型「否则不进入 P2」。实际交付的 P0 报告是**自动化技术验证报告**（31/31 PASS），没有任何学习效果数据。
2. **方案 A 名称里的「离线批量生成」经事实核查不成立**：ohmygame 无 `generate_game` / build / export / headless API，只有本机 MCP。可自动化的只有「审核 / 发布 / 托管」，「生成」仍是教研在桌面端人肉逐个操作。
3. **上线前提「常态化人工审核」无人承诺**：§11 #1 原文「若无法承诺常态化人工审核，方案 A 不具备上线条件，应只做方案 B」。仓库内无教研角色、无审核页面、无责任人、无周期。

同时，§4.3 ADR给的退出条件已经具备：「若做完 B 后『丰富度』已达标，A 可以不做」。方案 B 已交付 6 种参数化题型，§10 的「新增可玩交互形态 ≥ 6 种（方案 B）」已完成，**目前没有任何证据表明丰富度未达标**。

## 4. 「离线批量生成」的可行性硬伤

§1.3 的能力调研结论（`:53-65`）：

- ohmygame 是**本机 Electron 桌面应用**，无 npm SDK、无 REST/OpenAPI、无 headless / 服务器模式、无 iframe embed SDK；
- 公开的 20 个 MCP 工具中**没有 `generate_game` / build / export / static build**；`game_use` 是自动试玩，`generate_image/speech/music` 等是素材供给，`canvas_*` 是画布媒体；
- MCP 仅本机 stdio + `/external-mcp`，面向 coding agent，`external-agents.md` 明确把「user-configured HTTP entry」列为 not in scope；
- §1.3 关键推论：「NestJS 后端**无法**通过 HTTP 调用 ohmygame」，强行做即方案 C（已否决）。

因此方案 A 的现实形态是：

```text
教研在桌面端人工逐个生成 → 人工导出静态包
   → [可自动化] 注入 bridge / 静态扫描 / 状态机 / 审核留痕 / 发布 / nginx 托管 / iframe 投放
```

即 §6.2 SOP 的 **A1~A2 是人肉，A3~A6 才可脚本化**。「批量」实际是「批量审核与发布」，不是「批量生成」。

> **建议一并决策（Q2）**：把方案 A 重新定义为「**静态游戏内容受控上架管线**」，按此口径重估收益与人力。若产品真正想要的是「AI 批量产内容」，那属于已否决的方案 C，或需要另起自研生成器，与 ohmygame 无关，应另立议题而非挂在方案 A 下。

## 10. 与既有待办的关系

- **LLM 一次通过率生产基线采样（K.7）与方案 A 无依赖，且应排在前面**。脚本已就位，但需要教研给主题清单 + 授权真实 LLM 调用。若实测方案 B 一次通过率良好（例如 ≥85%），会进一步削弱方案 A 的必要性；若偏低，**应优先修方案 B 的 prompt / sanitize，而不是转向方案 A**——两者解决的是不同问题：A 是交互丰富度，B 的生成稳定性是质量，A 不能替代 B 的质量治理。
- 建议顺序：**K.7 基线采样 → G0-1/2/3 → Go/No-Go 决策**。两者都不需要改生产代码，可并行准备。
