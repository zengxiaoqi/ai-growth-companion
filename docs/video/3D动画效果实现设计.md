> 目标场景：小熊玩滑滑梯（从滑梯上滑下来）、小熊拍球（熊掌与球真实接触并反弹）。
> 文档状态：**方案 A（阶段 0–2）已实现并抽帧验收；方案 B 未实现**（注册表与渲染器枚举已留位）。
> 本文所有改造点均对应仓库当前代码位置。

与本文原设计的差异（实现时按仓库实际情况调整）：

1. **没有新增 `remotion-3d-*` 引擎枚举**。实际链路里 `agent-remotion` 与 `dynamic-remotion`
   是并列引擎，3D 只是渲染层差异，因此用「分镜含 3D 幕 → 优先内置模板」表达，
   避免动 `VideoRenderEngine` 的库表与 API 契约。
2. **3D 组件不进 GeneratedLesson 模板串**，而是作为独立 manifest 文件
   `three/ThreeActionStage.tsx` 随任务目录下发，模板只 `import`。源码在 Remotion 工程里
   可类型检查、可预览，由脚本转成字符串常量，避免两百多行几何代码挤在模板里。
3. **坐标不由 LLM 给**：prompt 只让模型写 `motion` + `actorId`，坐标一律来自注册表默认值，
   分镜里即使写了越界数字也会被 `normalizeAction3D` 丢掉。
4. **相机不抬 y**：R3F 默认相机 `lookAt(0,0,0)`，抬高相机会变成俯视（实测地面被拉到中线）。
   改为相机留 y=0、世界整体下移 `lookY`，取景才可算。

验收方式：`cd src/video-remotion && npm run typecheck:3d && npm run render:3d-check -- slide 0 45 89`
（脚本会把后端模板原样写成任务目录再渲染，等价于线上出片前半段）。

## 1. 背景与目标

### 1.1 现状

当前课程视频走的是「LLM 分镜 → 交互 DSL → 动态生成 Remotion TSX → MP4」链路：

- `src/backend/src/agent-framework/tools/impl/generate-video-content.ts` 生成 `StoryboardScene`，其中包含 `interaction` 字段（谁对谁做什么）。
- `src/backend/src/modules/learning/video/scene-interaction.ts` 用封闭动词（`handover | lift-together | speak | point | hold`）+ 开放角色/道具 id 描述关系，并可从旧文案确定性反推。
- `src/backend/src/modules/learning/video-generation-agent.service.ts` 的 `buildGeneratedLessonTsx()` 生成 `GeneratedLesson.tsx`，交互幕由 `ActionStage` + `ActorFigure` 演出，角色素材是 `staticFile("assets/vector/animals/" + actor.id + ".svg")`，动画靠 DOM/CSS 与帧号插值。

这套方案解决了「角色和道具都有、但关系丢了」的问题，但仍然是二维演出：角色是矢量贴图，动作是位移/旋转/缩放，无法表现「身体沿滑梯斜面滑下」「手掌在某一帧拍到球并让球弹起」这类连续三维接触关系。

### 1.2 目标

1. 角色是**有头、身体、四肢的完整三维形象**，不是熊脑袋贴图。
2. 滑梯幕：小熊从滑梯顶端沿斜面滑到底端，姿态随坡度变化，脚/身体与滑梯保持接触。
3. 拍球幕：熊掌与球在同一帧接触，球按可预期的弧线反弹，手臂角度与球高度同步。
4. 与现有分镜、旁白、字幕、TTS、审批/编辑/重新生成链路完全兼容。
5. 渲染结果确定性：同一输入、同一帧号永远得到同一画面，可重复出片。

### 1.3 非目标

- 不做影视级写实角色、不做面部表情绑定。
- 不让 LLM 直接生成 3D 模型；LLM 只产出结构化的动作描述。
- 不在第一版支持任意新角色自动建模；角色来自预置资产表。

## 2. 共用约束（两个方案都必须遵守）

### 2.1 Remotion 确定性渲染硬约束

`@remotion/three` 的 `ThreeCanvas` 在渲染期把 R3F 的 `frameloop` 设为 `never`，由 Remotion 帧号手动推进。因此：

- 禁止 `useFrame`、`requestAnimationFrame`、基于 `delta` / `clock.elapsedTime` 的自走动画。
- 骨骼动画必须用 `AnimationMixer.setTime(frame / fps)`，不能用 `mixer.update(delta)` 或 drei 的 `useAnimations`。
- 禁止 `Math.random()`；需要随机时用 `remotion` 的 `random(seed)`。
- 禁止自带时钟的 drei helper：`Float`、`Sparkles`、`Stars`、`Cloud`、`MeshDistortMaterial`、`MeshWobbleMaterial`、`CameraShake`、`AccumulativeShadows`、`Trail`。
- 若用 `ContactShadows`，需固定 `frames={1}` 或改为预烘焙阴影贴图。
- 物理不能实时跑（Remotion 跨标签页乱序渲染帧）；轨迹必须离线烘焙成每帧数据。
- 3D 内容必须包在 `ThreeCanvas` 内；`<Canvas>` / `ThreeCanvas` 显式声明 `layout="none"`。
- 异步加载（`useGLTF`、纹理、字体）放在 `Suspense` 下，`useGLTF.preload()` 在模块级预加载首帧模型。

## 4. 方案 A：纯代码参数化 3D

### 4.1 原理

不引入外部模型文件。用 Three.js 基础几何体拼出完整角色：`sphereGeometry` 做头和身体，`capsuleGeometry` 做四肢，`coneGeometry` 做耳朵，`cylinderGeometry` 做滑梯支架，`boxGeometry` 做滑板。所有运动由 `useCurrentFrame()` 计算出的数值驱动。

### 4.2 动作实现

**滑梯**：把滑梯抽象为从 `start` 到 `end` 的斜面。用 `interpolate(frame, [0, duration], [0, 1])` 得到进度 `t`，位置沿斜面线性插值并加轻微缓动；身体旋转从直立插值到后仰，四肢做摆动；`t` 到 1 时站起。

```tsx
const t = interpolate(frame, [0, 90], [0, 1], {
  extrapolateLeft: 'clamp', extrapolateRight: 'clamp',
});
const x = interpolate(t, [0, 1], [-3.2, 3.0]);
const y = interpolate(t, [0, 1], [3.4, 0.9]) - 0.25 * Math.sin(Math.PI * t);
const bodyTilt = interpolate(t, [0, 0.2, 0.85, 1], [0, 0.9, 0.9, 0]);
```

**拍球**：球高度用周期函数，接触帧固定在周期边界；手掌角度从同一个 `ballY` 推导，保证接触同步。

```tsx
const phase = (frame % 18) / 18;
const ballY = 0.45 + 1.2 * Math.abs(Math.sin(Math.PI * phase));
const pawRotation = interpolate(ballY, [0.45, 1.65], [0.35, -0.55]);
```

### 4.3 优缺点

- 优点：零美术资产、文件极小、完全确定、最快跑通链路、适合 POC 和「数学/图形」类主题。
- 缺点：造型是几何体卡通风格，真实感有限；复杂动作（翻滚、表情、毛发）难以表达。

### 4.4 适用

第一版优先实现，作为方案 B 的降级路径和视觉基线。

## 5. 方案 B：GLB 骨骼动画 + 烘焙物理

### 5.1 原理

角色、滑梯、球都是 GLB 模型。角色带骨骼与动画片段，渲染时用 `AnimationMixer.setTime(frame / fps)` 把动画锁到视频帧；球的弹跳和滑梯接触轨迹用 Rapier 离线烘焙成 JSON，渲染时按帧索引读取位置/旋转。

### 5.2 资产生产管线

1. **生成**：Meshy / Tripo（自动绑骨、有动画预设）、Hyper3D Rodin（高精度道具）、Hunyuan3D（开源可自托管）。角色生成时要求 A/T pose、四肢与身体分离，便于绑骨。
2. **修正**：Blender 中 remesh 降面（角色建议 1 万面以内）、修拓扑、统一朝向和原点、导出 GLB。
3. **绑骨/动画**：人形可走 Mixamo；四足或自定义骨架用 Mesh2Motion 或 Blender 手工。片段至少包含 `idle`、`slide-start`、`slide-loop`、`slide-end`、`dribble`。
4. **压缩**：`gltfpack` 或 Draco + KTX2，目标单角色 < 2 MB。
5. **入库**：放到 `src/video-remotion/public/assets/models/`，并在 `action3d-registry.ts` 登记 id 与片段名。

### 5.3 骨骼动画驱动

```tsx
const gltf = useGLTF(staticFile('assets/models/bear.glb'));
const scene = useMemo(() => SkeletonUtils.clone(gltf.scene), [gltf.scene]);
const mixer = useMemo(() => new AnimationMixer(scene), [scene]);

useEffect(() => {
  const action = mixer.clipAction(gltf.animations.find((c) => c.name === clip) ?? gltf.animations[0]);
  action.setLoop(LoopRepeat, Infinity).play();
  return () => mixer.stopAllAction();
}, [mixer, gltf.animations, clip]);

useEffect(() => { mixer.setTime(frame / fps); }, [frame, fps, mixer]);
```

注意：同一模型多实例必须 `SkeletonUtils.clone`，否则共享 skeleton 会互相污染；`useGLTF.preload()` 放在模块顶层。

### 5.4 离线烘焙物理

在 Node 脚本（不在 Remotion 渲染进程里）用 `@dimforge/rapier3d-compat` 以固定步长 `1 / fps` 模拟：

```ts
const world = new RAPIER.World({ x: 0, y: -9.81, z: 0 });
const ball = world.createRigidBody(
  RAPIER.RigidBodyDesc.dynamic().setTranslation(0, 4, 0),
);
world.createCollider(RAPIER.ColliderDesc.ball(0.35), ball);
const frames = [];
for (let f = 0; f < totalFrames; f += 1) {
  world.step();
  frames.push({ p: ball.translation(), r: ball.rotation() });
}
writeFileSync('public/assets/models/tracks/ball-dribble.json', JSON.stringify(frames));
```

渲染组件直接 `const pose = track[frame]` 设置 mesh transform。滑梯同理：把小熊沿滑面的接触点烘焙成轨迹，再与骨骼片段叠加。手球同步靠「烘焙接触帧 == 动画片段接触关键帧」对齐，必要时给 clip 加 `phaseOffset`。

### 5.5 优缺点

- 优点：真实角色形象与骨骼动作；接触、反弹、惯性自然；适合正式课程。
- 缺点：需要美术资产与绑骨；GLB 体积和无头 WebGL 渲染耗时上升；授权需核查；首版工作量明显大于方案 A。

## 7. 测试与验收标准

| 层级 | 检查项 | 通过标准 |
| --- | --- | --- |
| 单元 | DSL 解析 | 滑梯/拍球文案命中；总结句不误判 |
| 单元 | 缓存 | 渲染引擎或版本变化导致 cacheKey 变化 |
| 静态 | 生成 TSX | 无 `useFrame` / `Math.random` / `mixer.update(delta)` / 实时物理 |
| 静帧 | 滑梯 | 小熊包围盒中心 Y 随帧下降，末帧落在滑梯底端 |
| 静帧 | 拍球 | 球心 Y 呈周期性，最低点与熊掌位置重合 |
| 视频 | 连续性 | 抽 10 帧无黑帧、无角色跳变、无字幕重叠 |
| 性能 | GLB | 单角色压缩后 < 2 MB，首帧加载不超时 |
| 兼容 | 2D 回归 | 旧课程在 `remotion-2d` 下输出不变 |

## 8. 风险与对策

1. **无头 WebGL 慢**：保持低面数、单方向光、少后处理；避免 `AccumulativeShadows`。必要时先出方案 A。
2. **确定性被破坏**：任何 helper 引入前先 grep 其源码是否读 `performance.now()` / `Math.random()` / `delta`。
3. **模型体积**：生成阶段就限制面数，导出后 `gltfpack`，纹理 1K 起。
4. **授权**：Meshy/Tripo 免费档商用条款不同；生产使用前确认许可证，优先 CC0 或已购资产。
5. **LLM 乱填 id / 动词**：注册表白名单 + `normalizeSceneInteraction` 严格校验，非法即回落 2D 或默认角色。
6. **旧缓存命中**：缓存 key 带 `3d-v1`，并在编辑保存后 force 重生成，用户不会看到旧 MP4。
7. **多实例骨骼污染**：GLB 场景必须 `SkeletonUtils.clone`。
8. **接触不同步**：接触帧由烘焙轨迹单一数据源定义，骨骼 clip 只做相位对齐，不让两边各自算时间。

## 9. 选型建议与路线图

- **第一步做方案 A**：依赖少、可快速验证「关系 DSL → 3D 动作 → 确定性出片」整条链路，同时作为降级方案。
- **第二步做方案 B**：只在真正需要真实感的核心课程上启用，用 GLB 骨骼 + 烘焙物理；其余课程继续用 A。
- **长期**：把 `action3d` 变成与 `interaction` 平级的一等语法，LLM 直接产出动作意图，资产注册表决定具体模型与片段，业务代码不感知 model 细节。

## 10. 附录：关键术语

- **GLB / glTF**：Web 3D 资产格式，GLB 是单文件二进制版，可包含网格、材质、骨骼与动画片段。
- **AnimationMixer**：three.js 的动画状态机；确定性渲染时必须用 `setTime(frame / fps)` 而不是 `update(delta)`。
- **烘焙轨迹**：离线把物理模拟结果按固定帧率存成数组，渲染时按帧索引读取，保证乱序渲染也一致。
- **ThreeCanvas**：`@remotion/three` 提供的容器，把 R3F 渲染循环接管为 Remotion 帧驱动。
- **确定性**：帧是帧号的纯函数；同样的输入和帧号在任何渲染批次都得到同样画面。
